# Security boundaries and verification

This is the implementation contributor's design review and test record, **not an independent audit**. The later reviewer must inspect accepted source and the generated launch manifest together, including every constructor value and privileged beneficiary. Production handover also needs the founder's real-model rehearsal and acceptance. No deployment, paid work, owner transaction, real-model rehearsal or production handover is claimed here.

## Custody and authority

Refundable QRM is held only by QuorumSeats. Its only outgoing token path is a matured withdrawal to the recorded original depositor. The Safe, governor, agent and a new NFT owner cannot choose that recipient or confiscate a deposit. A new NFT owner may start the old deposit's exit to prevent indefinite blockage; the refund still belongs to the depositor. There is no slashing, admin emergency withdrawal or stake-funded treasury. Donations to the vault do not create claims and cannot be swept.

Owner-only admission configuration is a conscious trust boundary. The exact canonical IMD NFT address, admission count and source/hash were not supplied to this builder and are not guessed. They remain a one-time Safe setting, required before deposits. The source dataset must be checked against actual launch admission evidence; the contract cannot independently prove offchain connected-seat history. It verifies the launch token's fixed supply/decimals and the NFT's ERC-721 interface. A dishonest/upgradeable canonical NFT or a dishonest initial configuration can misrepresent ownership; the operator/reviewer must verify those external dependencies before acceptance.

ERC-721 `ownerOf` alone cannot detect an NFT transferred away and back between calls. The additional **exact per-token approval fuse** is deliberate: a conforming ERC-721 clears it on every transfer. The registry never exposes an NFT transfer function and never substitutes `isApprovedForAll`. Transfer away, transfer back, and approval revocation all disable the old key until the current owner explicitly restores the approval. Such explicit restoration can revive an otherwise unexpired authorization; owners should revoke/rotate before reapproving a reacquired NFT. No claim of an unavailable historical transfer nonce is made. A new owner cannot reuse another depositor's stake or frozen vote.

Authorization uses a separate key, finite expiry, scope bits, an incrementing version and independent agent consent. The token-transfer cap is a fixed K deposit from the owner to the vault with an explicit ERC-20 allowance, never a general wallet allowance to the key. Expiry/revocation/transfer blocks new signed actions even in old electorates. A fresh key can act for the same still-frozen deposit after explicit acceptance, but `hasVoted` prevents an additional vote. A new generation cannot borrow old attendance or a frozen claim.

## Participation, snapshots and liveness

ECDSA signatures use low-s/v checks and an EIP-712 domain bound to chain and Board address. Seat, key version, stake generation, chain hour, confirmed block number/hash, content revision/hash and status are all authenticated. Hour inclusion, block recency, exact historical revision and one credit/seat/hour are enforced onchain. Current-hour credit is excluded from activity. Signatures alone and late/offline backfill never count. This verifies responsiveness only, not comprehension or good faith.

Each snapshot scans at most **128 current deposits** atomically. It cannot omit an active qualifying seat by choosing a subset. Snapshot owner/generation and the entire electorate are fixed before voting begins. The bounded scan avoids relying on a central indexer or asynchronous ownership oracle. The limit is independent of N and applies to every entrant; capacity is a liveness tradeoff, and dormant deposits can occupy slots until their owners exit. It is not a claim of infinite permissionless capacity.

The maximum-capacity tests measure both a complete snapshot and a proposal containing eight calls / 4096 nonzero calldata bytes. Their NFT fixture uses ordinary owner/approval mappings. Actual canonical NFT gas costs must be measured during deployment review; contract size and bounded iteration do not guarantee that an arbitrarily expensive external NFT implementation is usable. The cap was chosen with headroom after a 256-seat measurement was too close to a transaction gas ceiling.

Exit removes the seat from future snapshots immediately. The seven-day delay exceeds every possible 72h voting interval, so even a frozen seat exiting immediately after a snapshot cannot withdraw before that vote closes. Dormancy never shrinks an existing electorate or quorum. Five remains the quorum floor, even when fewer than five seats are eligible. All seats can be offline; execution/receipts then stop. There is no implicit timer, central keeper or reduced-quorum rescue.

## Governance, spending and Safe 1.5.0

Ordinary proposals are typed budget transfers only. Budgets can be created only by the Safe during an executing major proposal and specify immutable asset, recipient, cap, purpose and expiry. Caps are checked again and consumed atomically at execution. Ordinary ERC-20 transfers check both Safe debit and recipient credit for the exact approved amount, as well as optional return convention, rejecting extra sender fees, short recipient credits, false returns and rebasing effects. Such assets need a separately explicit major call instead of silently breaking ordinary caps. Asset contract behavior remains a governance-reviewed external dependency.

Major actions store exact target/value/calldata and optional return hash onchain. Commitments bind chain, governor, nonce, seat, kind, work hash, constitution and rules. The deployment chain is checked again at execution. No supplied calldata substitutes for stored actions. Replay, double execution, early/expired execution, reentrancy and partial batch success are rejected. A failed batch rolls back execution markers, budget consumption, token movements and target state, and can be retried until expiry. No automatic gas subsidy or continuation is supplied.

Natural-language work classification is a governance responsibility: voters must reject a work proposal that omits its typed work specification. Contracts cannot infer that an arbitrary external CALL is paid development. When a work hash is declared, its full scope/resources/deadline/criteria bind the exact action commitment and execution needs a valid current acceptance. An acceptor may revoke it; expired/revoked/transferred/withdrawn/exiting authority no longer satisfies the gate. Ordinary dormancy alone does not undo an accepted responsibility.

Handover is gated by the founder's exact bundle acceptance, 10 active seats, 5 owner addresses, a frozen-genesis two-thirds yes vote, and the major vote/timelock. No deployment/time/IMD-status shortcut exists. The contract verifies actual Safe proxy/singleton code hashes and version, owners, threshold, the full bounded module list, both guard slots and fallback handler. Unexpected extra authority fails closed. The observed existing Safe has a fallback handler that must be removed during BOOTSTRAP before acceptance.

After handover the Safe owner is the governor contract, both guards are the governor, and the only module is the governor. All owner-path execution/refunds are rejected. Module execution requires CALL, the sole module identity, an exact current authorization hash and guarded callback ordering. All Safe self-calls are rejected, including owners, threshold, modules, guard/handler removal or singleton changes. No proxy/upgrader/emergency role exists in project contracts. Safe's public simulation delegatecall always reverts and cannot persist writes. Guard checks cannot be impersonated by a direct external call.

**Pre-existing external permissions are an operational prerequisite, not enumerable Safe storage.** A Safe guard cannot discover every ERC-20 allowance or third-party spending right already granted before installation. The founder/reviewer must exhaustively audit relevant history and revoke those rights before acceptance, as the handover checklist requires. An outstanding right remains a release-blocking finding, not a claim these contracts can erase it. A later major proposal approving an allowance intentionally delegates the exact reviewed power and must be assessed accordingly.

Immutable governance means there is no in-place authority/rule upgrade. Major-approved new applications and voluntary stake migration are supported, but the existing Safe remains under its original governor and payer identity. This is disclosed in the constitution; an unrestricted upgrade disguised as a release is not supported.

## Connector and publication

The connector's owner controls its dedicated key, scopes, model/RPC access, targets/selectors, fees and updates. Model output has a small validated schema; public text cannot add commands, permissions, destinations or configuration paths. No `eval`, shell dispatch, automatic update or governance-code execution is provided. Only public constitution/proposal/discussion content and bounded local rationale reach the model. A model can still make a bad decision within its vote permission; signature scope is not an intelligence guarantee.

Local state is bounded, atomic and single-process locked. Queue removal and pending signed transaction persistence happen before broadcast. A restart rebroadcasts the same bytes/nonce. Confirmed canonical receipts gate success and follow-ups; failures remain failures. Reorgs rewind checkpoints/caches/decisions; proposal commitment checks stop a queued action from changing meaning after ID reuse. A deep reorg or unresolved externally replaced nonce requires explicit owner reconciliation. The connector refuses gas outside finite owner limits, does not silently replace transactions, and cannot guarantee hourly inclusion.

RPC correctness, local file integrity, owner machine security, model availability and public IPFS/ENS hosting are external assumptions. The simple key file is plaintext with owner-only filesystem permissions, not an HSM. Release observations are untrusted reports. Approved hashes never prove that a gateway serves those bytes or that a CID remains pinned. Fetch, hash, compare, mirror and pin under the owner's policy. Hosting control and approved-versus-published hashes must remain visible in the separately produced frontend.
